# Publishing

`@sdwa/tokens`, `@sdwa/components`, and `@sdwa/lint-config` are versioned and published with
[`changesets`](https://github.com/changesets/changesets). This document describes the release flow.
For how to add a changeset to your own PR, see [`CONTRIBUTING.md`](./CONTRIBUTING.md).

> **Status:** the workflow described here is being built out under the
> [SDFWA Design System: npm Publishing Pipeline](https://linear.app/sdfwa-web-infra/project/sdfwa-design-system-npm-publishing-pipeline-e21f8a3632ac)
> map. This document reflects the decided design, not necessarily what's live yet — check the map
> for current status.

## How a release happens

The whole flow lives in one workflow, [`.github/workflows/release.yml`](./.github/workflows/release.yml),
built from [`changesets/action`](https://github.com/changesets/action)'s dedicated sub-actions
(not the combined action) so that each job carries the minimum permissions it needs.

1. A PR that changes a package's behavior includes a changeset file (see `CONTRIBUTING.md`).
2. Every push to `main` runs a `select-mode` job first, which inspects repo state and decides
   whether the workflow should version, publish, or do nothing this run.
3. **If there are pending changesets** (mode `version`): the `version` job opens or updates a
   standing **"Version Packages"** pull request — bumping the affected packages' versions, writing
   their `CHANGELOG.md` entries, and removing the consumed changeset files. This PR accumulates
   every pending changeset. This job only needs `contents: write`/`pull-requests: write` — no
   registry access, no approval gate.
4. **When a maintainer merges the Version Packages PR** (mode `publish`, since the changesets are
   now consumed and package versions no longer match what's on npm): the `pack` job builds every
   package and tars up the ones whose version changed, with no registry access at all. Its output
   artifact is handed to the `publish` job.
5. The `publish` job is gated behind the **`npm-publish`** GitHub Actions environment, which
   requires a maintainer's manual approval before it runs. Merging the Version Packages PR prepares
   the release; it does not, by itself, make anything public. A maintainer gets a notification to
   review and approve the pending deployment, and only then does `npm publish` actually run,
   authenticating via OIDC (see Authentication below).

> **Setup note:** the `npm-publish` environment and its required-reviewer rule must be created once
> in the repo's Settings → Environments — this is a repo-settings action a maintainer has to do by
> hand; it can't be scripted from outside GitHub's own permission model. Until it exists, GitHub
> auto-creates an unprotected environment on first use, which means the gate does nothing — confirm
> required reviewers are actually configured before relying on it.

## Versioning

- **Independent per-package versioning.** `@sdwa/tokens`, `@sdwa/components`, and
  `@sdwa/lint-config` each carry their own version and bump independently — a components-only
  change does not bump `tokens` or `lint-config`. There is no "fixed"/lockstep group.
- **Starting version**: all three packages remain at `0.1.0` for their first real npm publish.
  Crossing from "only in this repo" to "on the npm registry" does not by itself change the API's
  stability — `0.1.0` still means "may change," which is accurate for a design system with only
  five proof-of-concept components built so far.
- **Changelogs**: each package gets its own `CHANGELOG.md`, generated by `changesets` from the
  changeset descriptions that contributed to each release. There is no repo-wide changelog.

## Authentication

Each package's actual `npm publish` step authenticates differently depending on whether that
package has ever been published before.

1. **Bootstrap (once per package, ever)**: `@sdwa/tokens`, `@sdwa/components`, and
   `@sdwa/lint-config` each need one manual, human-run `npm publish` for their very first version.
   npm's trusted-publisher relationship (below) can only be configured for a package that already
   exists on the registry — there's no way to pre-register trust for a package name that's never
   been published. A maintainer runs `npm login`, then `npm publish` (with `--access public`, since
   `@sdwa` is a public scope) from each package's directory, once. No npm token is ever added as a
   GitHub Actions secret for this step.
2. **Ongoing, after bootstrap**: once a package exists, a maintainer configures a **trusted
   publisher** for it on that package's npmjs.com Settings page: repository
   `San-Diego-Fine-Woodworkers-Association/Design-System`, workflow filename
   `.github/workflows/release.yml`, no stored secret. The `publish` job authenticates via its own
   OIDC identity (`permissions: id-token: write`); npm verifies it against the configured trusted
   publisher and issues a short-lived credential for that one publish. This must be configured
   **separately for each of the three packages** — trusted publishing is linked per package name,
   not per repository.
3. **Locking it down**: once a package's trusted publisher is confirmed working (a real CI publish
   succeeds via OIDC), flip that package to **"Require two-factor authentication and disallow
   tokens"** on npmjs.com. This permanently retires any token-based publish path for that package —
   after this, only the linked GitHub Actions workflow (via OIDC) or a maintainer with 2FA can ever
   publish it again.

No npm token is stored as a GitHub Actions secret at any point in this flow — the only credential
that ever exists is a maintainer's own npm login, used three times, manually, for the bootstrap
publishes.

## Why an approval gate

This publishes to a public npm scope (`@sdwa`) with no prior release history and no easy way to
fully undo a bad publish (`npm unpublish` is restricted after 72 hours, and a broken version may
already be installed elsewhere by then). The extra manual approval step costs one click per
release and buys a last real chance to catch something wrong before it becomes public and
effectively permanent.
